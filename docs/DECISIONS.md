# 設計判断の記録（DECISIONS）

作業中に決めたこと・仕様から変えたこと・未対応のことを記録します。新しいものを下に追記します。

---

## 基盤

### D-01 Next.js 16 / React 19 を採用
- `create-next-app` の最新版（Next.js 16.4）で作成。
- 雛形で有効になっていた `cacheComponents` / `partialPrefetching` は外した。画面はほぼクライアント描画で、
  API は動的に動く Route Handler なので、キャッシュの仕組みを入れる利点がなく、挙動が読みにくくなるため。

### D-02 サーバーからの書き込みは Postgres への直接接続（postgres.js）で行う
- 仕様では「Route Handler → Supabase service role キー」だったが、supabase-js では複数テーブルにまたがる
  トランザクションが組めない（判定では「加点・勝者・フェーズ・山札」を同時に書き換える必要がある）。
- そこで `DATABASE_URL`（postgres ロール。RLS を通らない）で接続し、全操作を1トランザクションで行う。
  本番（Netlify の関数）では Supabase の接続プール（Transaction mode, 6543番）を使う前提で `prepare: false`。
- 結果として service role キーは不要になった。JWT の検証には anon key（公開してよい値）を使う。
- `DATABASE_URL` は service role キーと同等以上に強い権限なので、`NEXT_PUBLIC_` を付けないこと（`.env.example` に明記）。

### D-03 同じルームへの操作はルーム行のロックで直列化し、さらに version で楽観ロック
- すべての API は `select … from rooms where code = $1 for update` から始まる（`src/lib/server/roomContext.ts`）。
  同じルームへの同時操作は DB 側で順番待ちになり、二重実行は起きない。
- それに加えて、フェーズを進める API（advance / pitch/end / judge / round/next）はクライアントが見ていた
  `rounds.version` を受け取り、一致しなければ 409 を返す（仕様 5.1）。3台が同時にタイマー切れで advance を
  呼んでも、進むのは1回だけ（統合テストで確認）。

### D-04 JWT の検証
- `supabase.auth.getClaims(token)` を使用。非対称鍵（Supabase の新しい既定）なら JWKS で手元検証、
  対称鍵（ローカル環境など）なら Auth サーバーへ問い合わせる。結果は有効期限までメモリにキャッシュする。

### D-05 レート制限はメモリ内の簡易版
- 同一ユーザー・1秒あたり、操作系 5 回 / 状態取得 10 回（`src/lib/server/rateLimit.ts`）。
- Netlify の関数ではインスタンスごとに数えるので厳密ではない。厳密にするなら Upstash Redis などに置き換える（未対応）。

## ゲームロジック

### D-06 カードの本文は JSON が正、DB にはIDだけ
- `src/data/topics.json` / `words.json` を編集すればカードを変えられる。DB にカードのマスタは置かない。
- サーバーは手札の並べ替え・交換時に、カードIDが手札のものかを検証する。
- IDを消すと、進行中のルームでそのカードが表示できなくなるので、カードを消すときは遊んでいるルームがない時に行う。

### D-07 カテゴリ分散配布のやり方
- 1人1枚ずつ順番に配る。手札にすでにあるカテゴリのカードは飛ばし、飛ばしたカードは順序を保ったまま山札の上に戻す。
- 山札を最後まで見ても合うカードがなければ、捨て札を1回だけ混ぜ直して探す。それでもなければ条件を緩める
  （12カテゴリ×16枚あるので通常は起きない）。

### D-08 山札は「ラウンド終了時に捨て札へ」
- お題と手札はラウンドが終わって次のラウンドを配る直前に捨て札へ送る。そのラウンド中に配られたカードは
  山札にも捨て札にもないので、同じラウンドで同じカードが2人に渡ることはない。
- 再戦（もういっかい）では山札を作り直さず続きから使う。直前のゲームと同じカードが出にくくなる。

### D-09 切断・離脱の扱い（計画で承認済みの推奨案）
- 切断の判定：最後の通信（ハートビートは10秒ごと、ほかの API 呼び出しも含む）から25秒。
- 切断中の人にも手札は配る（戻ってくるかもしれないため）。発表の番が来た時点で切断中ならスキップし、
  `pitches.skipped = true` として記録する（カードは公開しない）。
- 親の巡回は seat_order 順。ラウンド開始時点で切断中・離脱済みの人は飛ばす。
- 準備完了の判定は接続中の子だけで行う（切断中の子を待たない）。
- ゲーム中のキック・退出は行を消さず `left_at` を入れる。以降の親・発表・配布から外し、得点の表示は残す。
  退出した人は同じルームに戻れない（ロビーでのキックは行ごと消すので、もう一度参加できる）。
- 人数不足時の「続行」は、そのまま続ける。接続人数が最少人数以上に戻ったら選択を解除し、また下回ったら再度確認する。
- 発表できる子が0人のラウンドは判定を飛ばし、勝者なしで結果表示へ進む。

### D-10 判定・次ラウンド
- 判定できるのは親。親が切断したまま判定フェーズが60秒続いたらホストも判定できる（仕様どおり）。
- 判定の候補は「このラウンドで実際に発表した人」。スキップされた人・親は選べない。
- 目標点に達したら、結果表示（スタンプ）を見せてから「次いこか」でゲーム終了画面へ進む。

### D-11 並べ替えは準備時間中だけ、メモは発表が終わるまで
- 発表の公平さのため、カードの並び順は準備フェーズの終了で確定する。メモは本人用なので発表中も編集できる。

## DB・セキュリティ

### D-12 hands は Realtime の配信対象に入れない（計画で承認済み）
- 手札が変わるのは本人の API 操作だけなので、API の応答で最新の手札を返す。
- RLS でも本人以外は読めないようにしてある（統合テスト `tests/integration/rls.test.ts` で確認）。

### D-13 players.auth_uid はクライアントから読めない
- 列単位の権限で `auth_uid` を外した。他人の匿名ユーザーIDは不要な情報なので見せない。

### D-14 追加した列
- `rooms.game_no`（再戦ごとに増える。振り返りを今のゲームに絞る）、`rooms.low_player_decision`、`rooms.version`
- `players.left_at`、`players.joined_at`
- `rounds.game_no`、`rounds.phase_started_at`（代理判定の60秒判定）、`rounds.ready_player_ids`（準備完了人数の表示）
- `pitches.room_id`（Realtime のフィルタ用）、`pitches.skipped`

### D-15 期限切れの削除
- pg_cron で毎時17分に `expires_at` を過ぎたルームを削除（関連テーブルは連鎖削除）。
- API でもアクセス時に期限を確認し、切れていれば削除して 410 を返す。
- どのルームにも属さない3日以上前の匿名ユーザーも毎日削除する。

### D-16 シードデータ
- ルームとプレイヤーは匿名ユーザーに結び付くため、シードでは作らない。`supabase/seed.sql` はマイグレーションの確認だけを行う。

## テスト

### D-17 統合テスト（Vitest + ローカル Supabase）を追加
- 仕様のユニットテスト・E2E に加えて、API の処理関数を直接呼ぶ統合テストを `tests/integration/` に置いた。
  権限・409・タイマー・切断スキップ・ホスト移譲・RLS を、ブラウザを使わずに数秒で確かめられる。
- `pnpm test:integration`（要 `supabase start`）。

## 画面・同期

### D-18 Realtime の通知は「取り直しの合図」として使う
- `rooms` / `players` / `rounds` / `pitches` の変更通知を受けたら、中身を個別に反映するのではなく
  `/api/room/state` で全体を取り直す（120ms のデバウンス付き）。状態のずれが起きにくく、処理が単純になる。
- ハートビートで `players.last_seen_at` だけが変わった通知は無視する（画面に影響しないため）。
- 購読が切れたら指数バックオフで購読し直し、つながった時点で全体を取り直す。念のため20秒ごとにも取り直す。
- 操作系の API はすべて最新のスナップショットを返すので、操作した本人の画面は通知を待たずに更新される。
- 取得結果は「後から始めた取得」だけを反映する（古い応答で新しい状態を上書きしない）。

### D-19 タイマーの自動進行
- 各端末が、補正済みのサーバー時刻で締め切りを過ぎたら `/api/phase/advance` を呼ぶ。殺到しないよう 0〜400ms ずらす。
- 端末時計のずれでサーバーに「まだ早い」（NOT_DUE）と言われたら1秒後に再挑戦する。
- 時計のずれは API 応答の `serverTime` と往復時間から推定し、往復が最も短かったサンプルを採用する（1分ごとに更新を許す）。
- 準備中に接続中の子が全員「いけるで！」済みなら（切断者がいて自動で進まなかった場合など）、同じく advance を呼ぶ。

### D-20 フォントは Google Fonts のスタイルシートを直接読み込む
- `next/font` は日本語フォントの分割ファイル（数百個）をすべて自前配信しようとして重いため、
  `<link rel="stylesheet">` で読み込み、ブラウザが必要な文字の分だけ取得するようにした。
- 本文 Zen Maru Gothic、単語カード Kiwi Maru、ロゴ・スタンプ Yusei Magic。

### D-21 手描き風の線について
- カードの縁は「不揃いな角丸」（`border-radius` の楕円指定）と「真下にずらしたベタ影」で表現した。
  SVG フィルターで線を揺らすと文字までゆがむため、カードには使わず、ハンコ（スタンプ）とロゴの「！」にだけ使っている。
- カードの傾き（-3°〜3°）はカードIDから決める。再描画のたびに角度が変わってガタつかないようにするため。

### D-22 効果音は WebAudio で合成
- 音声ファイルを持たず、「ポン」（配布・自分の番）と「パコン」（スタンプ）を WebAudio で鳴らす。既定はOFFで、
  ヘッダーのスピーカーボタンで切り替える（端末ごとに localStorage に保存）。

### D-23 並べ替えはドラッグと ▲▼ ボタンの両方
- dnd-kit のドラッグ（タッチは長押し150ms）に加えて、各カードに ▲▼ ボタンを付けた。片手操作やスクリーンリーダーでも並べ替えられる。

### D-24 PWA 名
- 仕様どおり manifest の `name` / `short_name` は `eeyan`。ホーム画面での表示を「ええやん」にしたい場合は
  `src/app/manifest.ts` の `short_name` を変える。

### D-25 招待URL
- 招待URLは `/room/<コード>`。未参加の人が開くとニックネーム入力だけの参加フォームが出る。
  スマートフォンでは「招待URLをコピー」で OS の共有シートを開く。

### D-26 ゲーム終了の流れ
- 目標点に達したラウンドの結果画面では、ボタンが「次いこか」ではなく「結果発表いこか」になり、押すとゲーム終了画面へ進む。
- ホストはゲーム中いつでも画面下の「ゲームを終える」で終了できる（確認ダイアログあり）。

### D-27 デプロイ先は Netlify
- 仕様では Vercel だったが、利用者の判断で Netlify にした。Next.js は Netlify の OpenNext アダプターで動き、
  Route Handler はサーバーレス関数になる。設定は `netlify.toml`（ビルドコマンドと Node.js 22）だけ。

### D-28 最少人数を2名に変更（利用者の指示）
- `MIN_PLAYERS` を 3 → 2 に変更。2人のときは親1人・子1人になり、判定の候補はその子だけになる（必ずその子に1点）。
- 人数不足の警告も「接続中の人数が2人を下回ったとき」に変わる。最大人数（8人）は変更なし。

### D-29 参考ゲームの文言は書かない（利用者の指示）
- 「このボールペンを1万円で売ってください」は参考にしたゲームの名称なので、画面・ドキュメントには書かない。
- お題カード t001（ボールペン）は同じ文面になるため削除した（IDは欠番のまま使い回さない）。

### D-30 「該当なし」を選べるようにした（利用者の指示）
- 仕様では「引き分け・該当なしは不可」だったが、2人プレイだと「買う／買わない」の二択になるため、親はいつでも「該当なし」を選べるようにした（人数に関係なく）。
- 該当なしのラウンドは誰にも点が入らず、結果画面は「今回は『ええやん』ならず」と表示する。API では `winnerPlayerId: null`。

### D-31 お題に合わせたヒント（利用者の指示）
- 単語カードの下に、お題の商品名を入れたヒントを表示する（例：「このビニール傘が今しか手に入らない理由は？」）。
- ヒントはカテゴリごとの文面（`src/data/categories.ts` の `hint`、`{item}` が「この＋商品名」に置き換わる）。
  `words.json` のカードに `hint` を書けば、そのカードだけ別の文面にできる。
- 表示するのは、準備中の自分の手札と、自分が発表している最中のカードだけ（見ている側には出さない）。
